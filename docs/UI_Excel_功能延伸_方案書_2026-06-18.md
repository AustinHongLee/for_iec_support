## 0. 給執行 agent 的鐵則（每個模組都適用，先讀這段）

這些是「無論做哪個模組都不能違反」的規則。違反任一條 = 該模組失敗，必須回退。

1. **計算真值不可碰。** 依 AGENTS.md 權威順序：`使用者指令 > 原圖/PDF > core/ > configs/data > tests/validate > docs/*.md > catalog`。本方案書大多數模組屬「呈現層／設定層」，**不應改變任何 BOM 數字、重量、尺寸、材質**。少數會碰 `configs/*.json`（計算真值）的模組，標題會標 **【碰計算真值】**，要用最高規格驗證（對 PDF／golden）。
2. **基線驗證是每個模組的開頭與結尾。** 動工前先跑、收工後再跑，輸出要一致或更好：
   ```powershell
   python -m compileall -q python_app
   python python_app\validate_tables.py            # 結尾須見「VALIDATION COMPLETE」
   python python_app\validate_tables.py | Select-String '^X'   # 須「無輸出」
   python -m pytest -q                              # 預期 40 passed（需 PyQt6）
   ```
   任何一項由綠轉紅、或 `validate_tables` 多出 `^X` 行 → **立即回退該模組**。
3. **一個模組 = 一個（或少數幾個）commit，不混雜。** 不要把換行正規化、邏輯改動、版面改動混進同一 commit。不要順手 revert 別人的變更。
4. **不刪檔、不搬大檔，除非模組明文要求且使用者已確認。** `.xlsx`／`.pptx`／`archive/**` 一律先留。
5. **Markdown（含本檔、`docs/types/*.md`、各種 `*_REPORT.md`）只是脈絡，不是真值。** 判斷 Type 行為一律回到 `core/types/type_XX.py` + `configs/type_XX.json` + `tests/`。
6. **不確定就停、回報，不要猜著做。** 尤其碰到型號、材質、尺寸對不上時。
7. **改了 `configs/type_XX.json` 的資料就要寫戳記**：補 `data_updated_at` 與 `data_update_note`（依 AGENTS.md「Data Update Rule」）。
8. **每個模組做完，更新該模組的「完成定義(DoD)」勾選，並把驗收指令輸出貼回。**

> 規模標記：**S**＝半天內、單檔或少數檔、純呈現；**M**＝1～2 天、跨數檔、需回歸測；**L**＝需先做 snapshot/golden 才能動、風險中高。

## 1. 現況診斷（為什麼要做這些）

本節是「問題根因」，不含實作。三個痛點都已對照實際程式碼確認。

### 1.1 UI：你「說不出哪裡不滿」，其實是這幾件具名的事

你的感覺（「一定能更好」但講不出）幾乎都來自下列**可命名、可量測**的問題，不是錯覺：

| 你體感到的 | 真正的成因（程式碼證據） | 屬於 |
|---|---|---|
| 畫面「擠、密、不透氣」 | 結果表 `font-size: 11px`、欄位多達 22～23 欄、列高未放大；`_apply_stylesheet` 全程小字級 11–12px | 資訊密度 |
| 「不知道眼睛該先看哪」 | 沒有視覺層次：標題、區塊、數據用的字級/權重差異太小，全是灰底白卡 `#F5F6FA`/`#FFFFFF` | 視覺層次 |
| 「看起來像舊工具、不夠俐落」 | 樣式直接內嵌在 `ui/main_window.py` 的 `_apply_stylesheet`（約 114–252 行）一大段字串，沒有設計變數（color/spacing/radius token），調一個顏色要翻程式 | 缺設計系統 |
| 「改一下就怕弄壞」 | `ui/main_window.py` 是 **2959 行、112 個函式的「上帝物件」**：UI、xlsx 匯入解析、欄位推斷、匯出流程全擠在一個 `MainWindow` 類別 | 結構耦合 |
| 「操作完不確定成功了沒」 | 忙碌/空狀態/錯誤提示散落、不一致（`_set_analyze_busy`、`_invalidate_analysis_outputs` 各自為政） | 操作回饋 |

**結論**：UI 不需要「重做」，需要的是「**先抽出設計系統 → 降密度 → 建層次 → 統一回饋 → 最後才拆檔**」。這順序讓每一步都看得到改善、又不會一次動太多。

### 1.2 匯出 Excel：長官說「資料多、但沒意義的部分很多」——他是對的

實際的 workbook（`export/excel/workbook.py`）一次產 **10 張表**，主要明細表欄位數：

- 「重量明細表」`_CALC_BASIS_HEADERS` = **23 欄**
- 專案明細 `PROJECT_HEADERS` = **22 欄**
- 「查核-支撐明細」`LEADER_DETAIL_HEADERS` = **16 欄**，且長官最關心的 **`型號` 排在第 8 欄**（前面是 狀態／類別／統計項目／來源圖號／流水號／數量／單位）

對長官沒意義、卻佔滿版面的欄位（內部追溯用）：`重量計算式`、`物件類別`、`製造方式`、`列型`、`來源圖號`、`流水號`、`輸入數量`、`輸入單位`、`零件ID`、`庫存ID`、`項次`。

**根因不是「資料錯」，是「一張表同時想服務三種人」**：長官（要結論）、採購（要數量/採購量）、工程稽核（要追溯）。三種需求疊在同一張寬表 → 對任何一種人來說都「一半是雜訊」。

**好消息**：你們其實已經做對了一半 —— `manager_cover_sheet.py` 的「長官-摘要」已經是「一頁只放結論、用超連結跳轉、不列型號來源」的正確範式。**問題是這個範式只用在封面，明細表還在傾倒全部欄位。** 解法是把「分角色視圖」往明細表推，且**用隱藏/分組，不用刪資料**（追溯欄留著，但預設收起來）。

### 1.3 功能延伸：三個你提到的需求，對應三個結構缺口

| 你的需求 | 現況 | 缺口 |
|---|---|---|
| 「某 type 內某常數變了，怎麼不用動程式本體？」 | 已有 `configs/type_XX.json` + `core/config_loader.py`，39/67 型號可「改 JSON 即可」 | 仍有約 **21 個 calculator-only 型號**把常數寫死在 `core/types/*.py`；且**沒有安全的編輯/驗證介面**，非工程師不敢直接改 JSON |
| 「01 type，換了別家設計公司，形狀一樣、東西差不多，但常數和編號型態不同（奇怪英文代碼）」 | 全系統**只有一份** `type_01.json`；`type_anchor_index.json` 有 `storage_alias`(01T→01) 與 `shared_spec`(52/53…→pipe_shoe) 概念 | **沒有「同形狀、不同來源(設計公司/專案)的變體 overlay」**：無法在不分叉整個型號的情況下，覆寫常數表 + 換掉 designation 格式 + 對應不同代碼 |
| 「建檔優化」 | `ConfigDialog`（唯讀顯示 table + 存檔）、`TypeManagerWidget`（瀏覽） | **沒有「從圖面引導建檔」流程**：沒有依 schema 產生的表單、沒有存檔前驗證、新增型號要手刻 JSON |

還有一個**地雷**：`core/config_loader.py` 的 `_config_path()` 用 `type_id.lower().replace('t','').zfill(2)`，等於假設「型號一定是兩位數字 + 可選 t」。一旦出現設計公司的英文代碼（你說的「奇怪英文代碼」），這個函式會**默默算錯路徑**。C 區第一個模組就先修它。

## 2. 模組總覽與執行順序

每個區塊都先做「地基模組」，後面的才有依靠。**可以一次只派一個模組給 agent。**

```
A. UI                B. Excel 匯出            C. 功能延伸
─────────            ──────────────           ─────────────
A1 設計token地基  ┐   B1 欄位用途分級(地基) ┐  C1 設定載入器強化(地基) ┐
A2 結果表降密度   │   B2 長官視圖瘦身       │  C2 設計公司變體overlay  │
A3 視覺層次間距   ├─   B3 跨表欄序中文化     ├─ C3 代碼別名/翻譯表      ├─（C1先行）
A4 操作回饋一致   │   B4 信心度標示         │  C4 常數外部化機制+示範  │
A5 拆god object   ┘   B5 匯出前preview(選)  ┘  C5 建檔精靈+驗證         │
A6 即時截圖診斷(選)                            C6 版本/來源戳記(選)     ┘
```

**相依規則（agent 必讀）：**
- A 區：**先做 A1**（其餘 A2/A3/A4 都依賴 token）；**A5 最後做**（風險最高，且 A1 完成後拆檔更安全）。
- B 區：**先做 B1**（B2/B3/B4 都讀 B1 的欄位分級表）。
- C 區：**先做 C1**（C2/C3/C5 都依賴強化後的載入器）；**C2 依賴 C3**（變體要先能對應代碼）。
- 三大區**彼此獨立**，可並行，但區內順序要遵守。

**建議優先序（若要排程）：** B1→B2（長官最有感、零碰真值） → A1→A2→A3（UI 體感、零碰真值） → C1→C3→C2（解設計公司問題） → C5（建檔） → 其餘選配。

## 3. Part A — UI 改善模組

> 全 A 區**不碰計算真值**。風險集中在「視覺回歸」（看起來跑掉），不是「算錯」。每個模組做完請**截圖前後對照**。

### 模組 A1：抽出設計系統 token（UI 地基）
- **解決什麼**：顏色/字級/間距/圓角散落、寫死在 `_apply_stylesheet` 字串裡，調一處要翻程式；後續所有 UI 模組沒有共同語彙。
- **動到的檔案（只動這些）**：新增 `python_app/ui/theme.py`；修改 `python_app/ui/main_window.py` 的 `_apply_stylesheet`（約 114–252 行）改為「讀 token 組字串」。
- **絕對不要動**：任何 `core/`、`export/`、`configs/`。不改任何功能行為。
- **前置依賴**：無（這是 A 區地基）。
- **實作步驟**：
  1. 建 `theme.py`，定義一組 token（dict 或 dataclass）：
     ```python
     # python_app/ui/theme.py
     TOKENS = {
         "color": {
             "bg": "#F5F6FA", "surface": "#FFFFFF", "ink": "#222222",
             "muted": "#6B7280", "primary": "#1565C0", "primary_weak": "#BBDEFB",
             "border": "#C8CDD5", "danger": "#C0392B", "ok": "#2E7D32",
         },
         "font": {"base": 13, "small": 12, "table": 12, "title": 16, "metric": 22},
         "space": {"xs": 4, "sm": 8, "md": 12, "lg": 18, "xl": 28},
         "radius": {"sm": 4, "md": 6, "lg": 10},
     }
     def build_stylesheet(t: dict = TOKENS) -> str:
         """回傳與現行視覺等價、但由 token 組成的 QSS 字串。"""
         ...
     ```
  2. 把現行 QSS 的數值換成 `build_stylesheet()` 產出（**第一版刻意做到視覺幾乎不變**，只是把硬編碼抽成 token，先確保等價）。
  3. `main_window.py` 改成 `self.setStyleSheet(build_stylesheet())`。
- **完成定義（DoD）**：app 啟動後外觀與改之前**幾乎一致**（這版只搬不改）；`grep -n "setStyleSheet" ui/main_window.py` 只剩一處呼叫 `build_stylesheet`。
- **驗收指令**：`python -m compileall -q python_app` 通過；手動啟動 `run_app.ps1` 截圖比對。
- **停損條件**：啟動報錯、或樣式明顯跑掉且無法快速修 → 回退。
- **規模**：S。

### 模組 A2：降低結果表資訊密度
- **解決什麼**：結果表 11px、欄太多、列太擠 → 「看了累」。
- **動到的檔案**：`python_app/ui/main_window.py`（`_apply_result_table_column_layout`(約576)、`_set_project_result_headers`(約571)、結果表建立處 `_build_center_panel`(約439)）；用 A1 的 token。
- **絕對不要動**：欄位的「資料內容」與順序所對應的計算結果；`export/`（匯出是另一條路，Part B 處理）。
- **前置依賴**：A1。
- **實作步驟**：
  1. 表格字級用 `TOKENS["font"]["table"]`(12)，列高 +4～6px，表頭加粗、凍結首列。
  2. **預設只顯示「人要看的欄」**（型號 / 品名 / 規格 / 材質 / 數量 / 總重），其餘追溯欄做成「顯示進階欄」開關（checkbox 或右鍵選單）切換 `setColumnHidden`。**只是隱藏，不刪欄、不改資料模型。**
  3. 數字欄右對齊、加千分位；文字欄左對齊。
- **完成定義（DoD）**：預設視圖欄數明顯變少、可一鍵展開全部欄；切換不影響匯出。
- **驗收指令**：`compileall` 通過；手動操作截圖；確認匯出檔欄位**不受影響**（跑一次匯出比對）。
- **停損條件**：隱藏欄導致匯出或篩選邏輯異常 → 回退到「只調字級/列高」的最小版本。
- **規模**：S–M。

### 模組 A4：操作回饋一致化
- **解決什麼**：忙碌/成功/失敗/空資料的提示不統一，使用者不確定「成功了沒」。
- **動到的檔案**：`ui/main_window.py`（`_set_analyze_busy`(約1754)、`_set_export_busy`(約2003)、`_invalidate_analysis_outputs`(約1624)、`_set_result_summary`(約1578)、狀態列 `QStatusBar`）。
- **前置依賴**：A1（用 token 的 ok/danger 色）。
- **實作步驟**：
  1. 統一一個 `_set_status(kind, text)`（kind ∈ ok/info/busy/error）集中控制狀態列顏色與文字。

- **驗收指令**：`compileall` 通過；手動跑「分析→匯出」全流程截圖。
- **停損條件**：狀態訊號與實際狀態不符（例如失敗卻顯示綠字）→ 回退。
- **規模**：S。

## 5. Part C — 功能延伸模組（低耦合）

> 這一區直接對應你提的三個需求。設計原則：**所有「不同來源的差異」都用「資料疊加(overlay)」表達，不靠改 calculator**。calculator 永遠只讀「合併後的設定」，因此新增一家設計公司＝新增一個檔，不動程式本體。

### 模組 C1：設定載入器強化（C 區地基，先修地雷）
- **解決什麼**：`core/config_loader.py` 的 `_config_path()` 用 `type_id.lower().replace('t','').zfill(2)`，假設型號＝兩位數字＋可選 t。一旦出現英文代碼會**默默指到錯檔**；也沒有「找不到就明確報錯」與「schema 驗證」。
- **動到的檔案**：`python_app/core/config_loader.py`（強化，保持既有函式簽章相容）；新增 `python_app/core/config_schema.py`（驗證用）。
- **絕對不要動**：既有對外函式名稱（`load_config`/`save_config`/`list_configs`/`get_type_table*`）的行為與回傳型別——只能往「更嚴謹」加，不可破壞既有呼叫端。
- **前置依賴**：無（C 區地基）。
- **實作步驟**：
  1. 重寫 `_config_path()`：改用「明確對照」而非字串砍 't'。先查 `type_anchor_index.json`（storage_alias / shared_spec），查不到再退回「`type_<id>.json` 檔存在性檢查」；**找不到要 raise 明確錯誤或回 None，不可猜路徑**。
  2. 加 `validate_config(config: dict) -> list[str]`（回傳問題清單）：檢查必要欄位（`type_id`/`name`/`designation_format`/`table` 等）與型別。
  3. `load_config` 增一個可選參數 `strict=False`；`strict=True` 時驗證失敗就 raise。預設行為不變（向後相容）。
  4. 加單元測試 `tests/test_config_loader.py`：含「英文代碼不會誤指到別的數字型號」這個關鍵案例。
- **完成定義（DoD）**：傳入含字母的代碼不再誤砍；既有 39 個 config 載入結果不變；新測試通過。
- **驗收指令**：`pytest -q`（多測試、仍全綠）；`python python_app\tools\find_type.py 01` 與 `51` 輸出與改前一致；`validate_tables` 無 `^X`。
- **停損條件**：任何既有型號載入結果改變 → 回退（代表破壞相容性）。
- **規模**：M。

### 模組 C2：設計公司／專案「變體 overlay」層【碰計算真值】
- **解決什麼**：你的核心痛點——「01 type 換了別家設計公司，形狀一樣、東西差不多，但常數和編號（奇怪英文代碼）不同」。現在只能整個型號分叉或改壞原檔。
- **做法總綱**：保留 `configs/type_01.json` 當**基準形狀(base)**；新增「變體 overlay 檔」只描述**差異**（不同的 L 表、不同 h_limit、不同 designation 格式、不同代碼）。載入時 `base ⊕ overlay = 合併設定`，calculator 照舊讀合併結果。**新增一家設計公司 = 新增一個 overlay 檔，零改程式。**
- **動到的檔案**：新增資料夾 `python_app/configs/variants/`；新增 overlay 範例 `configs/variants/type_01__acme.json`；在 `core/config_loader.py` 加 `load_config(type_id, variant=None)` 的合併邏輯（深層合併）；`core/config_schema.py` 加 overlay 驗證。
- **絕對不要動**：`configs/type_01.json` 基準檔的數值（base 不變，差異全進 overlay）。
- **前置依賴**：C1（強化後的載入器）、建議先有 C3（代碼別名）。
- **Overlay 檔 schema（給 agent 照著做）**：
  ```jsonc
  // python_app/configs/variants/type_01__acme.json
  {
    "schema": "type-variant/1",
    "base_type_id": "01",                 // 形狀來源：沿用 type_01 的 calculator 與結構
    "variant_id": "01@ACME",              // 本變體的唯一識別
    "source": {                            // 這份差異是誰、哪個專案
      "design_company": "ACME Engineering",
      "project": "P-2026-樂工",
      "drawing_no": "ACME-PS-01 Rev.A"
    },
    "merge": "deep",                       // 深層合併：overlay 有的欄覆寫 base，沒有的沿用 base
    "code_alias_ref": "type_01@acme",      // 對應 C3 的代碼翻譯表 key（把奇怪英文代碼對到內部欄位）
    "overrides": {                          // 只寫「和 base 不一樣」的部分
      "h_limit": 1800,
      "designation_format": {
        "pattern": "{vendor}-{shape}-{line_size}-{H_code}",
        "example": "ACME-PS01-200-12",
        "fields": { "vendor": "ACME", "shape": "PS01", "line_size": "管線尺寸(mm)", "H_code": "H 高度(×100)" }
      },
      "table_replace": [                    // 整表替換（與 base 的 L 值不同時）
        { "line_size": 2,  "pipe_size": "1-1/2", "schedule": "SCH.80", "L": 75 },
        { "line_size": 3,  "pipe_size": "2",     "schedule": "SCH.40", "L": 96 }
        // …ACME 的完整 L 表
      ]
    },
    "data_updated_at": "2026-06-18",
    "data_update_note": "ACME 專案首版，L 表依 ACME-PS-01 Rev.A 轉錄"
  }
  ```
  合併規則（寫進 loader）：`overrides` 內的純量／物件做 deep-merge；遇到 `table_replace` 就**整表換掉**（避免新舊表混用算錯）；overlay 沒提到的一律沿用 base。
- **實作步驟**：
  1. `load_config(type_id, variant=None)`：variant=None 時行為與現在完全相同（相容）；給 variant 時先載 base 再套 overlay。
  2. 合併後**必過 `validate_config(strict=True)`**，不合格就 raise，絕不回傳半套設定。
  3. **加 golden**：對 base（不給 variant）的輸出做快照，確保「沒用變體的既有流程一字不差」；再對 ACME 範例做一組對 PDF 的驗算 golden。
  4. designation 解析要能依 variant 的 `pattern` 解析（解析器若寫死格式，需參數化——若改動大，先只支援「查表/常數」覆寫，designation 格式覆寫列為下一步）。
- **完成定義（DoD）**：不給 variant 時，**所有既有型號輸出零變化**（golden 證明）；給 `variant="01@ACME"` 時，用 ACME 的 L 表/上限算出與 ACME 圖一致的結果。
- **驗收指令**：`pytest -q` 全綠（含新 base 快照與 ACME golden）；`validate_tables` 無 `^X`；對 ACME 至少一個型號**人工對照 PDF 驗算**。
- **停損條件**：base 快照有任一筆變動（代表污染了既有行為）→ 立即回退；ACME 算出與圖不符 → 停手記錄、回報。
- **規模**：L。
- **給 agent 的提醒**：這是整份方案書架構價值最高、也最容易「越做越大」的模組。**第一版只要打通「常數/表格覆寫」即可**（designation 格式覆寫可留第二版）；先小、先正確、先有 golden。

### 模組 C3：代碼別名 / 翻譯表（奇怪英文代碼 ↔ 內部欄位）
- **解決什麼**：不同設計公司的編號型態不同（你說的「奇怪英文代碼」）。要讓系統「看得懂」這些代碼對應到內部哪個型號/欄位。
- **動到的檔案**：新增 `python_app/configs/code_aliases.json`；在 `core/parser.py` 解析入口前加一層「先過別名」；被 C2 的 `code_alias_ref` 參照。
- **絕對不要動**：既有 `core/parser.py` 對標準型號的解析行為（別名只在「比對不到標準格式」時才介入，或依 variant 指定才啟用）。
- **前置依賴**：C1。
- **別名表 schema**：
  ```jsonc
  // python_app/configs/code_aliases.json
  {
    "schema": "code-alias/1",
    "aliases": {
      "type_01@acme": {                    // 對應 C2 overlay 的 code_alias_ref
        "maps_to_base": "01",
        "patterns": [
          // 把 ACME 代碼欄位對到內部語意；可用具名群組或欄位順序
          { "match": "^ACME-PS01-(?P<line_size_mm>\\d+)-(?P<H_code>\\d+)$",
            "to": { "line_size": "{line_size_mm}/25.4", "H_code": "{H_code}" } }
        ],
        "notes": "ACME 用 mm 標管徑、PS01 代表我們的 Type-01 形狀"
      }
    }
  }
  ```
- **實作步驟**：
  1. 解析時：標準格式優先；命中 variant/別名情境時，用 `patterns` 把外部代碼轉成內部欄位再丟進既有計算。
  2. 轉換**留痕**：把「原始外部代碼」存進結果的備註/來源欄，方便對帳。
  3. 加測試：ACME 代碼 → 內部欄位 → 與標準型號走同一計算路徑。
- **完成定義（DoD）**：能吃 ACME 代碼算出正確結果；標準型號解析不受影響。
- **驗收指令**：`pytest -q` 全綠（含別名測試）；標準型號 golden 不變。
- **停損條件**：別名層誤攔標準型號 → 回退（別名只能在明確情境啟用）。
- **規模**：M。

### 模組 C4：把剩餘 calculator-only 常數外部化（機制 + 一個示範）【碰計算真值】
- **解決什麼**：你問「常數變了怎麼不用動程式」。對已 JSON 化的 39 個型號已成立；但約 21 個型號（以 `tools/audit_table_json_coverage.py` 實際輸出為準）常數仍寫死在 `core/types/type_XX.py`，改它們仍要動程式。
- **動到的檔案**：**本模組只示範一個型號**（建議挑使用頻率高、表單純的，如稽核工具列出的其中一個），新增其 `configs/type_XX.json`＋`data/typeXX_table.py` bridge；calculator 改讀 config。其餘型號列為後續同法逐一處理（一模組一型號，不要一次全改）。
- **絕對不要動**：該型號的**計算行為**（只把「寫死的數字」搬到 JSON，結果要一字不差）。
- **前置依賴**：C1。
- **實作步驟（嚴格依 TYPE_DEFINITION_CONTRACT.md「Refactoring Existing Flat Types」）**：
  1. **先加 golden case**鎖定現況輸出。
  2. 把該型號的尺寸/規則表抽到 `configs/type_XX.json`，補 `data_updated_at`/`data_update_note`。
  3. 建 `data/typeXX_table.py` bridge 讀 JSON、保留舊 API（注意 JSON key 是字串，數值查表要轉型）。
  4. calculator 改呼叫 bridge/config，**行為不變**。
  5. 跑 `validate_tables.py` 與 `pytest`。
- **完成定義（DoD）**：該型號改成「改 JSON 即可調常數」；輸出與外部化前**完全相同**（golden 證明）；`audit_table_json_coverage.py` 的 calculator-only 清單少一個。
- **驗收指令**：`pytest -q` 全綠；`validate_tables` 無 `^X`；`python python_app\tools\audit_table_json_coverage.py` 確認該型號脫離 risk 清單。
- **停損條件**：golden 有任一筆變動 → 回退。
- **規模**：M（每型號）。

### 模組 C5：建檔精靈 + 存檔前驗證（建檔優化）
- **解決什麼**：新增/編輯型號目前要手刻 JSON（`ConfigDialog` 偏唯讀）。非工程師不敢碰，工程師也容易漏欄。
- **動到的檔案**：`python_app/ui/type_manager.py` 或新增 `ui/type_editor.py`；用 C1 的 `validate_config`、C2 的 overlay schema。
- **絕對不要動**：`core/` 計算；存檔仍走 `config_loader.save_config`（已自動寫 last_modified/change_log）。
- **前置依賴**：C1（驗證）；若要建變體則加 C2。
- **實作步驟**：
  1. **依 schema 自動產生表單**：讀 `config_schema.py` 的欄位定義動態生表單（少寫死 UI）。
  2. 提供兩種起點：「新建基準型號」與「以現有型號建變體 overlay」。
  3. **存檔前一定先 `validate_config(strict=True)`**：不過不准存，紅字列出缺哪欄。
  4. 存檔成功後提示「已寫入 configs/…，change_log 已更新」。
- **完成定義（DoD）**：能用表單新增一個型號或變體並通過驗證存檔；錯誤會被擋下且訊息清楚。
- **驗收指令**：手動建一個測試型號→驗證→存檔→`find_type.py` 找得到；`pytest -q` 綠。
- **停損條件**：驗證可被繞過而存進壞檔 → 修到擋住為止，否則不算完成。
- **規模**：M–L。

### 模組 C6：型號設定的版本／來源戳記顯示【選配】
- **解決什麼**：用了哪家設計公司的哪版資料，UI/匯出看不出來。
- **動到的檔案**：`ui/type_manager.py`（`_show_detail`）顯示 `source`/`version`/`last_modified`/`data_update_note`；匯出層可在備註帶上 variant 來源。
- **前置依賴**：C2。
- **完成定義（DoD）**：選到變體型號時，能看到「來自哪家公司、哪版圖、何時更新」。
- **規模**：S。
