# DeepSeek｜主介面與功能體驗獨立評議

## 1. 十行內總評

功能骨架紮實，分析、匯入、覆寫、材質確認、數據維護全線已通。但介面把「能做的事」和「該做的事」混在同一平面，使用者面對四個視覺區域（KPI 摘要列、主表、BOM 明細、側欄）缺乏明確的操作階層與完成路徑。核心摩擦不在少功能，而在**狀態回饋分散**（分析進度在狀態列、覆寫結果在側欄小字、完成度在標頭條）、**下一步不可見**（匯入後不知道「現在該做什麼」），以及**搜尋與篩選的責任邊界模糊**（文字搜尋與逐欄篩選並存但分工不清）。修復優先序應為：串連工作流狀態回饋 > 簡化篩選分工 > 重整理右側資訊密度。

## 3. 建議的資訊架構

主畫面各區責任重新定義如下：

```
┌─────────────────────────────────────────────────────────────┐
│ 專案標頭：清單名稱 │ 全域材質 │ 模式(概/精) │ 完成度:N/M    │
│                                          [匯出準備度指示燈]  │
├───────────────┬───────────────────────┬─────────────────────┤
│ [可折疊]      │  主表 (支撐總覽)      │  側欄                │
│ 輸入清單      │  ┌─────────────────┐  │  ┌────────────────┐ │
│ (僅批次操作   │  │狀態│Drawing│... │  │  │  PDF 圖面預覽  │ │
│  時展開)      │  │ ✓ │ ...   │... │  │  │  (可縮放)      │ │
│               │  │ ⚠ │ ...   │... │  │  └────────────────┘ │
│ 快速定位:     │  └─────────────────┘  │  ┌────────────────┐ │
│ [Drawing/     │                       │  │ 計算邏輯(唯讀)  │ │
│  流水號片段]  │  BOM 明細 + 單筆摘要   │  └────────────────┘ │
│               │  ┌─────────────────┐  │                      │
│ 篩選:         │  │品名│規格│重│... │  │  [核對模式 □]       │
│ [Drawing▾]   │  │ ...│... │..│... │  │  修正控制:           │
│ [流水號▾]    │  └─────────────────┘  │   接入方式 / 材質    │
│ [型號▾]      │                       │   查表值覆寫          │
│ [材質▾]      │  [顯示全部欄 □]       │   [復原] [還原預設]  │
│ [狀態▾]      │  [工程│採購│查核 ▾]   │                      │
│ [僅看待確認] │                       │                      │
├───────────────┴───────────────────────┴─────────────────────┤
│ [▶ 分析] [匯出▾] [建立清單▾]       狀態列: 就緒 / 分析中... │
└─────────────────────────────────────────────────────────────┘
```

**責任說明：**

- **專案標頭**：常駐全工作階段，顯示「這個專案處於什麼狀態」。匯出準備度指示燈整合目前分散的完成度資訊。
- **輸入清單**：預設折疊，僅在需要批次選取、套用材質或匯入時展開。日常工作以主表為唯一互動面。
- **主表**：一列一筆支撐，所有狀態（分析中／完成／錯誤／待確認）在此可見。快速定位框（原文字搜尋）放在主表上方，輸入即跳到匹配列。
- **BOM 明細 + 單筆摘要**：選中列後顯示該筆的 BOM 表格與重量摘要；視圖切換同時影響主表與明細。
- **側欄**：縮減為 PDF 圖面（上半）與計算邏輯（下半，唯讀）。修正控制區（原在側欄的覆寫表單）移到 BOM 面板旁或主表行內展開。
- **底部工具列**：分析、匯出、建立清單為三個主要動作按鈕；核對模式為全頁級模式開關。

## 5. 候選功能裁決

| # | 候選功能 | 裁決 | 理由 |
|---|---|---|---|
| 1 | 專案首頁／最近檔案／續接 | **稍後做** | 有價值但非目前瓶頸。目前使用者抱怨的是「開了之後不知道做什麼」，不是「找不到上次的檔案」。引導面板（改動 #6）可解決近憂；最近檔案功能在使用者累積多次專案經驗後自然產出需求 |
| 2 | 匯入前預檢中心 | **稍後做** | 目前 `ProjectImportPreviewDialog` 已提供 completeness summary 與警告。預檢中心的價值在於「修正建議」，但那需要更深層的資料驗證規則（例如型號格式校驗、Drawing 流水號重複偵測、管徑合理性檢查），這些規則本身需要業務積累 |
| 3 | 可儲存篩選／欄位視圖 preset | **稍後做** | 目前三組視圖（工程／採購／查核）已涵蓋主要場景。自訂 preset 在使用者尚未形成重複篩選習慣前是過度設計。等視圖功能被接受後再評估 |

## 6. 四個爭議題的明確立場

### 左側輸入清單去留

**立場：保留但預設折疊，一個專案週期後評估完全移除。**

理由：輸入清單目前承擔三項獨有功能——勾選啟用／停用、多選批次套材質、以及顯示覆寫標記摘要（⚠ 材質未定、自訂值等）。主表尚未具備行內勾選與批次選取能力。在 G4b-2 條件成立（主表可完整取代）前，折疊是低風險的中間狀態：日常工作只看主表，需要批次操作時一鍵展開。完全移除的條件是主表內建 checkbox 欄與右鍵批次選單。

### 搜尋與逐欄篩選的分工

**立場：文字搜尋改為快速定位（跳轉＋高亮，不隱藏列）；逐欄下拉保留為縮小範圍篩選。**

理由：目前兩者 AND 組合的設計（`apply_filter` 中 `all(term in text for term in terms)` AND 欄位篩選）將定位與篩選混為一談。在 Excel 式工作流中，定位（「這筆在哪？」）與篩選（「只看 SUS304 的」）是兩種不同的認知操作。分離後，文字框的行為變為：輸入→跳到第一個匹配列（Enter 跳到下一個）；欄位下拉變為：選擇值→隱藏不符合列。這與 Excel 的「尋找」vs「篩選」一致。

### 自動重新分析的回饋與撤銷

**立場：需要三層回饋——(1) 觸發提示、(2) 進行中狀態、(3) 完成後差異摘要。撤銷至少支援單步復原。**

理由：目前 450ms debounced auto-reanalysis 在技術上運作正確，但使用者體驗上是「改了東西→游標閃一下→數字可能變了」。缺乏中間狀態讓使用者不確定「系統有沒有收到我的修改」。建議：
- 觸發：修改控件的背景色在 debounce 期間變為淺黃（表示「已修改，即將重算」）
- 進行中：主表中該列狀態欄顯示「⟳」動畫
- 完成：該列總重數字若有變化，短暫閃爍綠色（變重）或紅色（變輕）300ms
- 撤銷：側欄／BOM 面板顯示「復原上次修改」，可連續復原至本次工作階段起始狀態

### 數據維護頁的目標使用者與權限邊界

**立場：目標使用者是「Type 資料管理員」（資深工程師或審查者），不是日常分析使用者。**

理由：此頁的設計（diff 預覽、sanity 檢查、圖號版次必填、golden 驗證提示）顯示它是高風險操作，需要審查紀律。目前的「基準資料」badge 暗示了這一點，但未明確說明。建議：
- 在頁面標頭加角色定位文字
- 在分析頁面的全部明細中，若 Type 版本非最新，顯示「Type XX 資料版本非最新（數據維護頁）」連結
- 暫不需要密碼或權限控制（使用者已說明目前只有一人），但文字警告應清楚
- 未來多使用者時，可考慮「鎖定／解鎖編輯」按鈕（類似 GitHub 的 Edit 模式）

## 7. 不建議做的事

| 項目 | 理由 |
|---|---|
| **全面重寫為網頁版** | 目前技術棧（PyQt6 + 本地檔案存取 + PDF 渲染 + Excel 匯出）對 Windows 桌面工程工具而言是合理選擇。重寫成本遠大於解決現有 UI 摩擦。使用者抱怨的是資訊架構，不是技術棧 |
| **加 AI 助手／對話式查詢** | 工程清單工具的核心價值是確定性與可追溯性。AI 建議材質或數值會引進不可審查的決策路徑，與 IEC 工程審查要求直接衝突 |
| **即時協作／雲端同步** | 目前使用者為單人，且 Excel 匯入匯出已是實質的協作介面（CSV round-trip）。雲端同步涉及資安、版本衝突與網路依賴，遠超目前需求範圍 |
| **自動化材質建議** | 材質確認是工程判斷，任何自動建議（「同管線等級自動填入」除外）都會創造「系統幫我下了什麼決定」的不透明性。目前的「未定（用預設概算）」明確標記是正確設計 |
| **過度動畫與 UI 裝飾** | PyQt6 的 QSS 動畫能力有限，過度追求 Material Design 式轉場會增加維護成本且可能引入渲染 bug。功能回饋（閃爍、顏色變化）優先於裝飾性動畫 |
| **在主表加入行內編輯所有欄位** | 主表的價值是快速瀏覽，行內編輯會增加誤觸風險。目前覆寫控制在側欄／BOM 面板是更安全的設計。唯一可考慮行內編輯的是「備註」欄 |
| **將全部明細分頁移除** | STATUS.md 與施工單明確認定「全部明細」保留觀察。它是匯出對帳與全欄檢視的唯一入口，移除會喪失重要參考視角 |

## 9. 需要使用者回答的問題

1. **誰在使用數據維護頁？** 是分析工程師自己（發現表值有誤就順手改），還是有一位資深審查者專門維護 Type 資料？這決定該頁應該留在 Tab 還是獨立為「管理模式」。
2. **材質確認的實際工作流是什麼？** 是對著 PDF 圖面逐筆核對（核對模式），還是先全部跑概算、匯出清單給別人填、再匯入合併（CSV round-trip）？這兩種模式對 UI 需求差異很大。
3. **目前最常用的篩選操作是什麼？** 是搜尋特定 Drawing 下的所有支撐，還是篩出某種材質的所有項目，還是只找一筆特定的流水號？這決定搜尋／篩選重構的優先方向。
4. **700+ 筆清單的效能感受如何？** STATUS.md 記錄 0.524s 首次分析、0.061s 欄位篩選，但使用者實際感受是否流暢？有沒有特定操作（例如匯出、切換視圖）覺得卡頓？
5. **左側輸入清單在過去一個專案週期中使用了哪些功能？** 是否只用過勾選？是否有批次選取套材質的需求？還是幾乎只看主表？這直接決定 G4b-2 的去留裁決。

## 10. 最終只選五項

如果只能做五件事：

| 順序 | 改動 | 理由 |
|---|---|---|
| **1** | 主表選中高亮 + 重算狀態回饋 | 這是所有後續工作的地基。如果使用者不知道「選了哪筆」「改了之後算完沒」，任何功能改善都建立在模糊的知覺上 |
| **2** | 匯出準備度指示燈 | 目前使用者完成分析後的最大困惑是「可以匯出了嗎？」。一個三色指示燈直接回答這個問題，成本極低 |
| **3** | 文字搜尋改快速定位（不隱藏列）| 解決最常見的操作摩擦：在 700 筆中找一筆。目前的搜尋＋隱藏行為讓使用者迷失在「剩下的列去哪了」 |
| **4** | 核對模式提升為主表層級開關 | 材質確認是最耗時的工作流。將核對模式從隱藏 checkbox 提升為可見模式開關，直接加速這個步驟 |
| **5** | BOM 面板整合修正控制（側欄縮減）| 從六個視覺區域減為四個，是最直接的「不那麼擠」的結構修正。且順便解決修正與結果不在同一視線的問題 |
