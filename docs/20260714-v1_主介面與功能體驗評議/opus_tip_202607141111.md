# Opus｜主介面與功能體驗獨立評議

> 本評議以目前 `main` 實作為真值（`python_app/ui/main_window.py`、`support_master_table.py`、`project_import_dialog.py`、`data_maintenance_page.py`、`project_header.py`、`bom_detail_panel.py`），並對照 `docs/STATUS.md` 與 `施工單_G1-G4`。凡文件與程式衝突處，以程式為準並標明。未閱讀任何其他模型的 tip 檔。

## 1. 十行內總評

1. 這不是「功能不足」的工具，而是「能力已到位、但責任邊界與狀態訊號散落」的工具；G1–G4e 清單裡列的能力，程式裡幾乎都找得到對應實作。
2. 最大的問題是**同一件事有多個入口與多個訊號源**：材質確認完成度同時出現在 KPI 列與專案標頭；「數據維護」同時是工具列按鈕又是主分頁；篩選同時有左側快篩、中央自由文字、中央逐欄下拉三套。
3. 主表已是「一列一支撐」（`support_master_table.py`），但它是唯讀的，所有編輯仍得回到左側清單或側欄，導致左清單無法退場——這是責任沒切乾淨，不是缺功能。
4. 自動重新分析在覆寫後 450ms debounce 觸發，且有 busy／ok 文案，但**回饋只落在側欄「修正」分頁**，且從不告訴使用者「重量變了多少」，這是狀態模型缺一塊。
5. 完全沒有 Undo／Redo 或本階段變更紀錄；批次套材質、單筆覆寫都無法一鍵回退，只能靠「還原為 Type 預設」清空全部，對工程防誤操作是明顯缺口。
6. 匯入其實已有引導對話框＋xlsx 欄位對應確認＋匯入前完整度摘要＋警告，體驗鏈條相當完整；缺的是把「跳過列、缺漏筆」列成可逐列點回去修的清單，而非只給數字。
7. 「概算／精算」已接通且在匯出時真的生效（硬擋＋例外放行留痕），但切換模式當下只丟一句狀態列訊息，畫面零變化，使用者不知道切了有沒有用。
8. 數據維護頁是整個工具**設計最成熟**的一頁（依據必填、即時 diff、大幅變動確認、golden 提示、未存保護俱全），現在缺的是變更歷史與來源附件，而非安全機制。
9. workflow E（完成與匯出）沒有一個「完成檢查區」把輸入完整／分析完成／材質歸零／可匯出四件事收在一起；目前只能靠匯出鍵是否可按來間接判斷。
10. 結論：接下來該做的九成是**收斂與訊號整併**（把重複入口併掉、把狀態集中、把回饋補上 delta），只有「待處理問題佇列」「影響比較」「變更歷史」三項屬於真正新增，且都能用小步實作。

## 3. 建議的資訊架構

主畫面維持單一「重量分析」工作頁三欄，但把**責任重新切乾淨**：

- **頂部專案標頭（常駐、唯一狀態真相）**：清單名｜全域材質｜模式（概算/精算）｜完成檢查四燈（輸入／分析／材質／可匯出）。材質完成度只留在這裡，KPI 列不再重複。
- **左欄＝輸入與清單管理**：新增／貼上／匯入／載入四個對等入口＋一條只作用於輸入清單的快篩＋分析鈕。在主表可完整增刪改之前，左欄不移除（見 §6）。
- **中欄＝結果與尋找**：KPI 列（去掉材質確認，改放「本次重量變化」）＋逐欄篩選（主力）＋全域快尋（副）＋主表/BOM/全部明細。視圖 preset 與進階欄二選一語意。
- **右欄＝單筆情境**：圖面／修正／計算結果／計算說明。自動重算的 busy/ok 訊息升級到頂部標頭，右欄只留「這一筆」的細節。

## 5. 候選功能裁決

1. **專案首頁/最近檔案/續接** — **稍後做**。目前無專案持久化模型，載入靠 `_on_load_file` 單檔。價值中等但需先有「專案存檔格式」。最小版：記住最近 5 個匯入路徑放首開空狀態，成本 S。
2. **匯入前預檢中心** — **稍後做（部分已具備）**。欄位對應（`main_window.py:1273`）、完整度摘要、警告（`project_import_dialog.py:203-238`）都在，缺的是把三個順序對話框整併成一頁、並把跳過列列成可點清單。屬整併非新建。
3. **可儲存的篩選/欄位視圖 preset** — **稍後做**。已有工程/採購/查核三固定 preset；使用者自訂儲存價值有，但需求密度未證實。先觀察三固定 preset 是否夠用。
4. **單筆/批次 Undo/Redo 或本階段變更紀錄** — **現在做**。這是目前最痛的防誤缺口（批次套材質不可逆）。最小版做「復原上一步」即可，不必完整 redo 樹。
5. **統一「待處理問題」佇列** — **現在做（小版）**。材質未定（已有「僅看待確認」）、匯入缺漏、分析錯誤目前分散三處。最小版：完成檢查區點「材質 3 筆未定」即套用待確認篩選跳第一筆，串起既有零件即可，不必新建佇列引擎。
6. **修改前後重量/BOM 影響比較** — **現在做（重量層級）**。重量 delta 成本 S 且價值高（見改動 2）。BOM 逐項 diff 稍後做。
7. **舊 Type 版本影響提示與重算** — **稍後做**。已有資料版本足跡（`:2199-2206`），但「專案綁定版本 vs 目前版本」的比較需要專案存檔先落地。屬 C2 overlay 相鄰議題，勿與暫緩的 C2 混做。
8. **Type 維護變更歷史/版本回復/來源附件** — **變更歷史＝現在做；版本回復/附件＝稍後做**。change_log 已在寫入（`save_config(change_desc=...)`），把它讀出來成本 M；版本回復牽涉檔案版本管理，且與 golden 基線流程衝突風險高，須裁決。
9. **大型清單鍵盤/固定欄/欄寬排序記憶/效能回饋** — **稍後做（效能已達標）**。實測 704 列 0.5s，效能非瓶頸；欄寬/固定欄是體感優化，排在結構收斂之後。
10. **右側區改抽屜/分頁/獨立視窗/情境面板** — **不建議（維持現狀微調）**。右側已是分頁（修正/結果/說明）＋PDF，結構合理。改抽屜會讓「邊改邊看圖」變不方便。只需把 apply 訊息移出右欄升到標頭。
11. **我認為更值得做的 1–3 項**：
    - (a) **完成檢查區**（見改動 1）——比多數候選更能解「下一步不明顯」。
    - (b) **狀態訊號去重**（材質完成度、數據維護入口、三套篩選）——零新功能、直接降擁擠。
    - (c) **重量 delta 回饋**（改動 2）——用最小成本補上狀態模型最缺的一環。

## 6. 四個爭議題的明確立場

**左側輸入清單去留** — **保留，但明確定位為「輸入管理欄」，暫不移除**。理由：主表 `support_master_table` 目前 `NoEditTriggers`（唯讀），啟用勾選、刪除、右鍵批次套材質、單筆選取都只在左清單。要移除左清單，得先讓主表能勾選啟用／刪除／就地編輯 Drawing、流水號、數量——這正是 STATUS 中 G4b-2 的前提。立場：**先把「編輯 Drawing/流水號/數量」從選單對話框（`:355`）搬進主表就地編輯，跑完一個真實專案週期後再評估移除**，符合 STATUS.md:50 與施工單 G4b-2「條件未成立」。

**搜尋與逐欄篩選分工** — **逐欄篩選為主、全域快尋為輔、左快篩限定輸入清單**。目前三者語意重疊是「搜尋價值低」主因。逐欄下拉（Drawing/流水號/型號/材質/狀態）是工程核對的主力，應維持；中央自由文字改名「全域快尋」並明確涵蓋逐欄涵蓋不到的欄（品名、計算說明）；左側快篩標籤改為「篩選輸入清單」點出它不影響結果表。驗收：使用者能一句話說出三個框各自作用。

**自動重新分析的回饋與撤銷** — **回饋要升級、撤銷要補上**。目前 debounce 450ms＋busy/ok 文案（`:2150-2156`）方向正確，但兩個缺口：一是回饋埋在側欄修正分頁，看主表時看不到，應升到頂部標頭並補「±% 重量變化」；二是完全無撤銷，批次套材質不可逆。立場：**回饋升級為全域＋delta；撤銷做「本階段復原上一步」，範圍嚴格限輸入/覆寫/批次，永不觸及 BOM/重量/Type 計算真值**（守 §7 與施工單 G-鐵則1）。

**數據維護頁的目標使用者與權限邊界** — **目標使用者＝少數受信任的資料維護者（工程主管/標準負責人），非一般清單操作者**。現行邊界設計正確：可編輯僅 `h_limit/h_unit_mm/applicable_range` 與查表（`data_maintenance_page.py:42`），結構與公式唯讀（`:197-199`），儲存需圖號＋版次＋說明、大幅變動需勾選、存後提示 golden。此邊界應維持，**不要開放結構/公式編輯**。建議加的是可追溯性（變更歷史、來源附件）而非放寬權限。可編輯欄範圍是否需含更多常數，需使用者裁決（見 §9）。

## 7. 不建議做的事

- **不要移除左側輸入清單**（在主表具備完整增刪改與勾選之前）——會讓啟用/刪除/批次操作無處可去。
- **不要把右側情境區改成抽屜或獨立視窗**——會破壞「邊改邊看圖與結果」的核心動作。
- **不要在數據維護頁開放結構、公式、Type 計算欄位的直接編輯**——違反可追溯與防誤原則，且與 golden 基線流程衝突。
- **不要做完整 Undo/Redo 歷史樹**——工程場景只需「復原上一步」防手滑；完整 redo 樹成本高、狀態管理易出錯。
- **不要把所有動作塞進確認對話框**——目前匯入已是「引導→對應→預覽」三連 modal，再加會更煩；改用行內狀態與可展開清單。
- **不要新建獨立的「待處理問題佇列」引擎**——先用完成檢查區串接既有的「僅看待確認」「錯誤 KPI」「匯入警告」，證實需求再抽象。
- **不要碰匯出的數字、欄序、格式**——守施工單 G-鐵則1，本評議所有建議皆為新增區塊或 UI 層。
- **不要用「改網頁版/加 AI 助手/全面重寫」處理上述問題**——它們全是資訊架構與狀態訊號問題，桌面工具內小改即可解，重寫只會丟掉已成熟的數據維護與匯出防呆。

**第一波：立即修正（零新資料、零計算風險，1 個開發週期）**
- 去重：移除工具列 ⚙ 數據維護鈕（`:268`）；材質完成度只留標頭。
- 完成檢查四燈＋重量 delta 回饋（改動 1、2）。
- 三套篩選語意收斂與標籤釐清（改動 4）。
- 自動重算 apply 訊息升到頂部標頭（改動 2 附帶）。

**第二波：結構調整（需界定狀態快照/列號回傳，2–3 個週期）**

- 匯入預檢逐列清單化（改動 7）。
- 主表就地編輯 Drawing/流水號/數量，為 G4b-2 鋪路（§6）。

**第三波：具備資料/裁決後再做**

## 9. 需要使用者回答的問題

1. 數據維護頁目前只開放 `h_limit / h_unit_mm / applicable_range` 與查表四欄，實務上還有哪些「已確認常數」需要在 UI 直接維護？哪些絕對不可開放？
2. 「復原上一步」的範圍：只需輸入清單與覆寫，還是也要能復原「載入檔案取代清單」這種大動作？
3. 專案是否需要「存檔/續接」概念（即一個可再開啟的專案檔），還是維持「每次從 Excel 匯入」的無狀態流程？這決定候選 1、7 能不能做。
4. 概算與精算在你們流程中的實際分界點是什麼（誰在什麼階段切精算）？這影響完成檢查區與模式回饋的設計。
5. Type 資料變更後的「來源附件」通常是什麼形式（PDF 圖、Email、簽核單）？決定附件欄要連結還是內嵌。
6. 工程/採購/查核三個視圖是固定夠用，還是常有人想自訂欄位組合？決定候選 3 的優先序。
7. 施工單 G4e 提到需要 3–5 張日常操作截圖做二輪診斷——能否提供？可讓上述優先序用實際畫面再校準。

## 10. 最終只選五項

如果只能做五件事，依序：

1. **完成檢查四燈**（輸入/分析/材質未定/模式＋可匯出）——直接解「下一步不明顯」與「能不能發包看不出來」，成本 S，是所有工作流的收斂點。
2. **自動重算的重量 delta 回饋**（前→後 ±%）——補上狀態模型最缺的一塊，回答「改了之後結果變多少」，成本 S。
3. **本階段「復原上一步」**——補上唯一的重大防誤缺口（批次套材質不可逆），守住工程防誤，且嚴格不碰計算真值。
4. **狀態與入口去重**（材質完成度、數據維護入口、三套篩選）——零新功能、最低成本直接降低「資訊擁擠」與「功能責任不清」，這正是使用者主訴。
5. **匯入預檢逐列清單化**——把已具備的欄位對應＋完整度摘要，從「只給數字」升級為「指出哪幾列要修」，讓最抽象的匯入環節變得可操作。

理由：這五項全部落在使用者主訴的四個真問題（擁擠、責任不清、下一步不明、修改後狀態不直覺）上，四項是收斂與訊號整併（低風險），僅一項（復原）為新增且已限定不觸計算真值；沒有任何一項改動 BOM／重量／材質／Type 計算，符合全部評議約束。
